1. Introducción

H2O Please es una aplicación web frontend orientada al seguimiento diario de la hidratación. Su finalidad es ofrecer una herramienta sencilla, visualmente clara y fácil de utilizar para registrar el agua consumida, consultar el progreso respecto a un objetivo diario, revisar el historial del día y gestionar información básica del perfil del usuario.

El proyecto ha sido desarrollado como una aplicación estática ejecutada íntegramente en cliente, sin backend ni base de datos remota. La persistencia de datos se resuelve mediante localStorage, lo que permite mantener el estado del usuario y de la aplicación sin depender de infraestructura adicional. Como complemento funcional, el dashboard incorpora una tarjeta meteorológica que utiliza APIs externas para mostrar información contextual del clima local.

Esta memoria técnica presenta el estado real del proyecto, describe su arquitectura, documenta las decisiones de diseño adoptadas, expone el enfoque de integración seguido por el equipo y recoge los principales retos técnicos resueltos durante el desarrollo y la consolidación final del producto.

2. Objetivos y alcance

2.1 Objetivo general

El objetivo principal del proyecto ha sido construir una aplicación web de frontend capaz de facilitar el seguimiento diario de la hidratación del usuario mediante una experiencia de uso simple, comprensible y funcional.

2.2 Objetivos específicos

  • Permitir el registro local de usuarios mediante un sistema básico de login y registro.
  • Registrar manualmente la cantidad de agua consumida a lo largo del día.
  • Mostrar el progreso del usuario frente a una meta diaria de hidratación.
  • Mantener un historial de tomas con posibilidad de eliminación individual.
  • Gestionar datos básicos del perfil, especialmente edad y peso.
  • Recalcular el objetivo diario a partir del peso del usuario.
  • Persistir la información de uso localmente sin backend.
  • Incorporar un modo oscuro persistente por usuario.
  • Integrar una weather card en el dashboard como información contextual adicional.
  • Mantener una estructura de código modular y comprensible en JavaScript vanilla.

2.3 Alcance de la versión final

  • Login y registro local con username y password.
  • Inicio de sesión automático si existe una sesión activa.
  • Dashboard con navegación entre las vistas HOY, HISTORIAL y YO.
  • Alta manual de consumo de agua.
  • Historial diario de tomas con borrado individual.
  • Persistencia del estado del usuario en localStorage.
  • Recalculo del objetivo diario a partir del peso.
  • Edición de edad y peso desde la vista de perfil.
  • Persistencia del modo oscuro.
  • Integración de una weather card en el dashboard.
  • Página independiente de preview para la tarjeta meteorológica.

2.4 Elementos fuera de alcance

  • Backend o servicios de servidor.
  • Base de datos remota.
  • Autenticación segura para un entorno de producción.
  • Sincronización entre dispositivos.
  • Pruebas automatizadas.
  • Pipeline de integración o despliegue continuo.
  • Gestión avanzada de usuarios o permisos.

4. Arquitectura del sistema

4.1 Visión general

La aplicación sigue una arquitectura modular en frontend. Aunque no se utiliza ningún framework, sí existe una separación clara de responsabilidades entre páginas, lógica de aplicación, persistencia local, renderizado del DOM y consumo de servicios externos.

Los puntos de entrada principales son los siguientes:

  • index.html + scripts/index.js: acceso, login y registro.
  • dashboard.html + scripts/dashboard.js: panel principal de la aplicación.
  • weather-preview.html + scripts/pages/weatherPreviewPage.js: vista aislada de prueba para revisar la weather card; existe como recurso técnico, pero no tiene acceso directo desde la interfaz principal de la aplicación.

4.4 Responsabilidad de los módulos principales

UserConsumption

Es el modelo de dominio principal. Representa el estado persistente del usuario y centraliza operaciones asociadas al consumo de agua. Entre sus responsabilidades destacan almacenar la información principal del usuario, mantener el historial de tomas, recalcular el objetivo diario en función del peso y actualizar consumo, tiempos y alarmas asociadas al registro de agua.

App

Actúa como coordinador general del dashboard. Se encarga de cargar el usuario activo, comprobar si ha comenzado un nuevo día, inicializar la interfaz, escuchar eventos de interacción, actualizar la interfaz principal y delegar el renderizado de vistas secundarias.

DOMManager

Centraliza el acceso a nodos del DOM y el render inicial del dashboard. Esta decisión reduce búsquedas repetidas y mejora la legibilidad de la lógica de interfaz.

Navigation

Aísla la navegación entre HOY, HISTORIAL y YO, reduciendo el acoplamiento entre la lógica del dashboard y la gestión visual de secciones.

Views

Agrupa el renderizado de vistas secundarias, especialmente historial y perfil, con el objetivo de descargar a App.js de parte de la lógica de presentación.

storage

Gestiona la persistencia local en localStorage y actúa como capa intermedia entre la aplicación y el almacenamiento del navegador.

authService

Se encarga del flujo local de autenticación y registro, incluyendo compatibilidad con estados previos del proyecto.

4.5 Persistencia y sesión

Toda la persistencia de la aplicación se realiza en localStorage. Esta decisión permite que el proyecto funcione sin backend, aunque introduce limitaciones claras de seguridad y portabilidad.

Clave Finalidad
currentUser Usuario con sesión activa
userConsumption:<username> Estado persistido del usuario
H2O_PLEASE_WEATHER_API_KEY API key opcional para OpenWeather
localWeatherSnapshot Último snapshot meteorológico válido
Nota técnica: la persistencia local es adecuada para una aplicación académica de demostración, pero no debe interpretarse como una solución válida para autenticación de producción.

5.5 Consideraciones sobre el flujo de datos

La aplicación sigue un flujo de datos relativamente directo: el usuario interactúa con formularios o controles del dashboard, la lógica de aplicación valida y transforma la acción, el modelo o los servicios actualizan el estado, el estado se persiste en localStorage y la interfaz se vuelve a renderizar.

En la feature de clima se añade un paso adicional: la obtención de datos externos, su adaptación a un snapshot común y su almacenamiento en caché para evitar que fallos puntuales degraden la experiencia de usuario.

6. Diseño y decisiones de UX/UI

6.1 Criterio general de diseño

La interfaz final prioriza rapidez de uso, claridad visual y una experiencia consistente en pantallas reducidas. La base visual consolidada del dashboard se mantiene como referencia principal de integración, mientras que las mejoras posteriores se aplican con un criterio conservador para no romper el equilibrio alcanzado entre estructura, identidad visual y funcionalidad.

6.2 Decisiones de experiencia de usuario

Navegación en tres vistas

La división del dashboard en HOY, HISTORIAL y YO responde a una organización por intención de uso: HOY concentra la acción principal y la información de mayor frecuencia; HISTORIAL ofrece trazabilidad diaria del consumo; y YO agrupa la información de perfil y configuración básica.

Formulario de acceso unificado

La pantalla de acceso utiliza un único formulario con cambio de modo entre inicio de sesión y creación de cuenta. Esta decisión mejora la continuidad del flujo, evita duplicaciones de interfaz y reduce la complejidad visual.

Priorización de la acción principal

La vista HOY se diseña alrededor de la acción más relevante del producto: registrar consumo de agua con rapidez. Por ello se priorizan visualmente el objetivo diario, el total acumulado, el formulario de registro, el progreso alcanzado y la información meteorológica contextual.

Persistencia de preferencias

El modo oscuro se guarda por usuario, lo que favorece la continuidad de uso y refuerza la percepción de una aplicación con estado persistente.

Vuelta al dashboard tras guardar perfil

Después de actualizar el perfil, la interfaz regresa automáticamente a la vista HOY. Esta decisión reduce pasos innecesarios y devuelve el foco a la funcionalidad principal de la aplicación.

6.3 Integración visual de la weather card

La weather card no se plantea como una pantalla independiente dentro del flujo principal, sino como un componente contextual integrado en el dashboard. Esta decisión es coherente con el alcance del proyecto: el clima no es el centro del producto, sino un complemento que enriquece la experiencia.

En la versión final revisada, la tarjeta incorpora además un mensaje compacto de hidratación en función de la temperatura máxima prevista. Esta ampliación se diseñó como una mejora visual y contextual, manteniendo el bloque dentro de la propia card y limitando su altura para no penalizar la experiencia en pantallas móviles.

6.4 Criterios visuales observables en la versión final

  • coherencia visual entre login y dashboard
  • estructura compacta próxima a una experiencia de app móvil
  • navegación inferior con iconografía clara
  • contraste suficiente entre áreas funcionales
  • integración prudente de nuevas funcionalidades sin rediseño global

7. Gestión del trabajo del equipo

7.1 Organización del trabajo

El proyecto se ha organizado mediante Git y GitHub, con una estrategia basada en ramas de trabajo y una rama común de integración. La estructura funcional de ramas identificada en la documentación interna responde al siguiente esquema:

  • main: rama estable o de cierre
  • dev: rama común de integración
  • feat/...: ramas específicas por funcionalidad
  • docs/...: ramas y materiales de documentación

Este enfoque permitió desarrollar funcionalidades en paralelo y controlar la integración por fases.

7.2 Estrategia de integración

La documentación interna del proyecto muestra que la consolidación final no se realizó mediante merges ciegos de ramas completas, sino a través de una integración selectiva, priorizando una base visual estable y rescatando únicamente la lógica funcional útil cuando existía riesgo de romper el dashboard.

El criterio de integración seguido puede resumirse en tres principios:

  1. mantener una fuente de verdad visual clara
  2. integrar funcionalidad útil con cambios mínimos
  3. evitar arrastrar estilos o refactors globales de alto riesgo en fases tardías

8. Desafíos técnicos y soluciones aplicadas

8.1 Integración de ramas divergentes

Problema: el proyecto evolucionó en varias ramas con cambios funcionales y visuales mezclados, lo que elevaba el riesgo de inconsistencias tras los merges.

Solución aplicada: se tomó una base visual clara como referencia y se integraron otras aportaciones de forma selectiva y quirúrgica, priorizando lógica útil y evitando arrastrar estilos o refactors globales innecesarios.

Resultado: se mantuvo una versión final coherente y estable sin comprometer la identidad visual consolidada.

8.2 Persistencia sin backend

Problema: la aplicación debía conservar sesión, perfil y consumo sin infraestructura de servidor.

Solución aplicada: se diseñó una persistencia local apoyada en localStorage, con una capa específica de almacenamiento y reconstrucción del estado del usuario.

Resultado: se obtuvo un MVP funcional y fácil de ejecutar, adecuado para el alcance académico del proyecto.

8.3 Compatibilidad con usuarios de fases previas

Problema: la evolución del proyecto introdujo password en momentos posteriores, lo que podía generar incompatibilidades con usuarios creados en estados anteriores.

Solución aplicada: la lógica de autenticación incorpora compatibilidad con estados heredados, evitando romper la continuidad funcional.

Resultado: se preservó la usabilidad del sistema tras la evolución del modelo de autenticación local.

8.4 Reinicio diario del consumo

Problema: el consumo debía reiniciarse al comenzar un nuevo día sin apoyo de backend ni tareas programadas.

Solución aplicada: la aplicación compara la fecha actual con la última fecha registrada al cargar el dashboard y reinicia el estado diario cuando corresponde.

Resultado: se garantiza un comportamiento diario coherente con una implementación local sencilla.

8.5 Integración del clima con resiliencia básica

Problema: una feature dependiente de APIs externas puede fallar por permisos, red, ausencia de API key o indisponibilidad del proveedor.

Solución aplicada: se diseñó una integración con proveedor principal, fallback, caché local y snapshot normalizado para la interfaz.

Resultado: la weather card aporta valor funcional sin convertir el dashboard en una pantalla frágil o dependiente de un único servicio.

Extensión aplicada: sobre esa base ya resiliente se añadió una recomendación breve de hidratación basada en la temperatura máxima prevista del día. La ampliación reutiliza el mismo snapshot meteorológico, evita modificar la lógica central del consumo y mantiene un coste de integración bajo.

8.6 Crecimiento del coordinador principal

Problema: la lógica central del dashboard tendía a concentrar demasiadas responsabilidades.

Solución aplicada: se extrajeron módulos específicos para navegación, vistas y utilidades, descargando a App.js de parte del renderizado y la gestión de secciones.

Resultado: la estructura final resulta más mantenible y más legible desde el punto de vista académico.

8.7 Regresiones menores tras integración

Problema: en la fase final de integración aparecieron pequeñas regresiones de flujo y comportamiento.

Solución aplicada: se realizaron validaciones manuales sobre ramas de pruebas y se aplicaron correcciones mínimas, reversibles y focalizadas.

Resultado: se estabilizó el comportamiento esperado sin necesidad de rediseñar la aplicación.

9. Conclusiones

H2O Please alcanza un estado final coherente como MVP frontend orientado al seguimiento diario de la hidratación. La aplicación cumple su objetivo funcional principal, ofrece una experiencia de uso clara, incorpora persistencia local suficiente para el alcance del proyecto y demuestra una organización modular razonable en JavaScript vanilla.

Desde una perspectiva técnica, el proyecto destaca por varios aspectos: resuelve un flujo completo de uso sin backend, integra autenticación local, persistencia, perfil, historial y dashboard, añade una feature externa de clima con una resiliencia adecuada para el nivel del proyecto y evidencia un esfuerzo real de integración entre ramas y aportaciones del equipo.

El aprendizaje principal no reside únicamente en la implementación de funcionalidades, sino en la consolidación progresiva de trabajo paralelo sin degradar la coherencia del producto final. La adopción de una base visual de referencia, la integración selectiva y la modularización funcional han sido factores decisivos para obtener una versión estable y entregable.

Como líneas de mejora futuras, serían razonables las siguientes:

  • incorporar validaciones y accesibilidad más completas
  • añadir pruebas automatizadas
  • separar con mayor claridad documentación funcional y técnica
  • evolucionar la autenticación hacia un backend real si el proyecto creciera
  • reforzar la trazabilidad de gestión con anexos externos si la evaluación lo requiere

En conjunto, el proyecto presenta una base sólida para una entrega académica, siempre que la documentación final se acompañe, en su caso, de los anexos de validación que exija la rúbrica.
